# Releases are gated on a complete scenario run

## Context

Unattended publish is still the goal after the one-time npm setup: no required reviewer on the `npm` environment. Past releases elsewhere were cut by trivial commits. A merge of docs, chore, ci, test, refactor, or style work must not become a version. A green unit-test job is not the product DoD.

## Decision

1. Nothing in `push` to `main`, and no ordinary commit type, starts a release. `docs`, `chore`, `ci`, `test`, `refactor`, and `style` never change the version. The release workflow has no branch trigger.
2. A product release happens only when a machine-checked manifest lists every required scenario for the exact commit SHA, each `passed` on the first attempt, with spec check and the CI gates passed on that same SHA. Missing, skipped, retried, or stale evidence fails closed.
3. The release workflow creates the `v*` tag after those gates. Agents do not create tags, do not call `npm publish`, and do not open GitHub Releases. The only role that may start the workflow is the release role, and only through that workflow.
4. `mode=check` packs and rehearses and does not tag or publish. specfold's `bootstrap` workflow mode is not adopted. The `0.0.0-stage` name claim stays a one-time manual npm publish and is not a release.

## Consequences

The publish job can stay free of a human approval click and still refuse to run for a trivial SHA. Evidence from an older commit, or a row that passed only on a second attempt, does not count. The rule and the scenario list live in [[sot:svgif/release-gate]]. The definition of done in [[plan:svgif/20261110122000]] is not met until this gate passes.
